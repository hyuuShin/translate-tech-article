클라우드의 Claude Code: 클라우드 세션 활용 가이드

Claude Code in the cloud: a field guide to cloud sessions

클라우드 세션은 작업마다 새로운 VM에서 Claude Code를 실행합니다. 실제 세션 네 가지와 클라우드 세션에 적합한 워크플로 일곱 가지, 그리고 막히지 않고 GitHub를 연결하는 방법을 소개합니다.

Cloud sessions run Claude Code on a fresh VM for each task. Four real sessions, seven workflows that suit them, and how to connect GitHub without getting stuck.

Claude Code를 자신의 노트북 터미널에서 실행하는 경우가 많을 것입니다. 이 세션은 세 가지 면에서 노트북에 의존합니다.

  • 작업 트리(working tree)를 공유하므로, 한 저장소에서 두 세션을 실행하면 같은 파일을 수정하거나 같은 포트를 두고 충돌할 수 있습니다.
  • 사용자의 자격 증명으로 실행됩니다.
  • 컴퓨터가 절전 모드로 들어가거나 Wi-Fi 연결이 끊기면 중단됩니다.

클라우드 세션은 Claude Code를 별도의 머신에서 실행합니다. 작업마다 새 가상 머신이 할당되고, 저장소가 새 브랜치에 클론되며, 환경 설정도 이미 완료된 상태입니다.

세션은 claude.ai/code, Claude 모바일 앱, 데스크톱 앱, 터미널, Slack에서 시작할 수 있습니다. 시작한 세션은 브라우저, 모바일 앱, 데스크톱 앱에서 확인할 수 있습니다. 작업이 끝나면 결과가 브랜치에 남으며, 이를 풀 리퀘스트(pull request)로 만들 수 있습니다.

클라우드 세션은 Pro, Max, Team, Enterprise 요금제에 추가 비용 없이 포함되어 있습니다. 클라우드 머신에 대한 별도 요금은 없으며, 세션은 Claude Code의 다른 기능과 같은 사용량 한도를 적용받습니다. 요금제에 따라서는 조직 소유자가 먼저 클라우드 세션을 활성화해야 할 수도 있습니다.

이 가이드를 위해 작은 샘플 저장소를 대상으로 실제 클라우드 세션 네 개를 실행했습니다. 가이드 전반에 이 세션들의 트랜스크립트, diff, 소요 시간이 나옵니다. 스크린샷 속 저장소와 사용자는 가상으로 만든 것이며, 작업 내용, 출력, 수치는 모두 실제 세션에서 나온 것입니다.

클라우드 세션의 큰 장점 중 하나는 여러 작업을 서로 간섭 없이 동시에 실행할 수 있다는 점입니다. 아래는 16초 이내 간격으로 시작한 세 세션이며, 각각 별도의 머신에서 실행되었습니다. 노트북에서였다면 이 작업들을 차례로 실행하거나, 서로 충돌하지 않도록 신경 쓰느라 시간을 썼을 것입니다.

세 가지 작업, 하나의 저장소, 세 대의 머신

샘플 저장소는 가상의 항구 세 곳의 조수를 예측하는 작은 Node API인 tidepool입니다. 여기에는 흔한 문제가 세 가지 있었습니다. 테스트 하나가 네 번 중 한 번꼴로 실패했고, API 문서가 코드에서 더 이상 읽지 않는 파라미터를 설명하고 있었으며, 로거가 문자열을 이어 붙여 로그 줄을 만들고 있었습니다.

문제마다 하나씩, 16초 이내 간격으로 클라우드 세션 세 개를 시작했습니다. 세션은 프로그램으로 시작했고, tidepool이 GitHub에 없기 때문에 각 세션은 먼저 프롬프트에 담긴 파일로 저장소를 다시 만들었습니다. 실제 저장소라면 이 단계는 필요 없고, 터미널에서는 세션마다 claude --cloud 명령 하나면 됩니다. 줄여서 소개하면 세 프롬프트는 다음과 같았습니다.

CODEShell 
claude --cloud "npm test fails maybe one run in four. Find the flaky test, fix the root cause in the code (not the test), and prove it by running the suite at least 30 times in a row."
claude --cloud "docs/API.md is out of date with src/server.js. Rewrite it so every endpoint, parameter, default and response shape matches the code. Start the server and run each curl example to check it."
claude --cloud "Make src/logger.js emit one JSON object per line, keep LOG_LEVEL, and log method, path, status and duration_ms as fields. Add a test for the logger."

세션은 각각 61초, 65초, 72초 동안 실행되었고, 세 세션 모두 첫 세션이 시작된 지 87초 만에 끝났습니다. 저장소를 다시 만드는 데 각 실행 시간의 약 3분의 1에서 절반을 조금 넘는 시간이 걸렸습니다. 결과는 다음과 같습니다.

  • 불안정한 테스트(flaky test). Claude는 TtlCache.get에서 경쟁 상태(race condition)를 찾아냈습니다. 캐시가 로더 실행이 끝난 뒤에야 값을 저장했기 때문에, 로드 중에 같은 키로 get을 한 번 더 호출하면 로더가 다시 호출되었습니다. Claude는 캐시가 진행 중인 프로미스(promise)를 저장하도록 바꾸고, 로드가 실패하면 해당 항목을 삭제하게 했으며, npm test를 연속 40회 실행해 실패가 0건임을 확인했습니다.
  • 문서. Claude는 서버를 시작하고 모든 엔드포인트에 curl을 실행해, 기존 문서가 틀린 부분을 다섯 가지 찾아냈습니다. API가 반환하지 않는 필드가 나열되어 있었고, 코드가 무시하는 days 파라미터가 문서화되어 있었으며, 높이가 미터가 아닌 피트로 적혀 있었고, /next-high 엔드포인트가 빠져 있었으며, 오류 응답이 누락되어 있었습니다. 또한 형식이 잘못된 from= 값을 보내면 빈 목록이 200 응답으로 반환된다는 사실도 발견했는데, 요청받지 않은 서버 코드를 수정하는 대신 이를 주의 사항으로 문서화했습니다.
  • 로거. Claude는 JSON 로거를 작성하고, 요청 로그를 구조화된 필드로 옮기고, 테스트 다섯 개를 추가했습니다. 이 커밋에는 실패하는 테스트가 하나 포함되어 있었고, Claude는 캐시 테스트를 여덟 번 다시 실행해 그중 다섯 번 실패하는 것을 확인한 뒤, 그 원인이 첫 번째 세션이 고치고 있던 것과 같은 경쟁 상태임을 추적했습니다. 같은 해결책을 제안했지만 캐시는 작업 범위 밖이라 건드리지 않았고, 요약에서 테스트 스위트가 깨끗하지 않다고 밝혔습니다.

logger 세션의 결과는 클라우드 세션이 병렬 작업에 적합한 이유를 보여 줍니다. 각 세션은 저장소 사본, 프로세스, 브랜치를 독립적으로 가지고 있었습니다. docs 세션과 logger 세션은 테스트를 위해 각각 API 서버를 실행했지만, 서로 영향을 주지 않았습니다. 노트북 한 대에서 두 에이전트가 하나의 체크아웃을 함께 사용하면 같은 파일을 수정하게 되고, 각자 다른 포트를 지정하지 않는 한 포트도 충돌합니다.

이러한 격리 때문에 logger 세션은 첫 번째 세션이 작업 중이던 캐시 수정 사항에 접근할 수 없었습니다. 병렬 작업은 파일 경계를 기준으로 나누고, 브랜치는 적절한 순서로 병합하십시오. 또한 다른 세션이 이미 수정 중인 문제를 특정 세션이 보고할 수 있다는 점도 염두에 두어야 합니다.

CLAUDE CODE 클라우드 세션의 내부 구조

클라우드 세션은 Anthropic이 관리하는 인프라, 또는 자체 호스팅 환경(self-hosted environment)을 사용하는 경우 조직의 자체 머신에서 실행되는 Claude Code 세션입니다. 그림은 각 구성 요소를 보여 줍니다. 그림 뒤의 네 가지 핵심 사항은 작업 방식에 변화를 줍니다.

  • 모든 작업은 각자의 머신을 사용합니다. 저장소가 새 브랜치에 클론된 새 VM이 제공되므로 세션끼리 서로의 파일이나 포트를 건드릴 수 없습니다. 설치된 항목을 참고하십시오.
  • GitHub 토큰은 VM에 들어가지 않습니다. 프록시가 토큰을 보관하며, 세션은 자신의 작업 브랜치에만 푸시할 수 있는 단기 자격 증명을 받습니다. GitHub 프록시를 참고하십시오.
  • 저장소의 Claude 설정은 함께 전달되지만, 개인 설정은 전달되지 않습니다. CLAUDE.md, 규칙, 스킬, 에이전트, 명령어는 저장소와 함께 전달되고, ~/.claude는 노트북에 그대로 남습니다. 클라우드 세션의 설정을 참고하십시오.
  • 유휴 상태의 VM은 회수됩니다. 세션을 다시 열면 대화가 복원된 새 VM이 제공되므로, 중요한 작업은 커밋해 두십시오. 환경 만료를 참고하십시오.

사양, 권한 모드, 네트워크 수준에 대해서는 클라우드 환경 문서를 참고하십시오.

로컬과 클라우드 중 선택

클라우드 세션이 로컬 세션을 대체하는 것은 아니며, 대부분의 사용자는 둘 다 사용합니다. 표는 두 방식의 차이를 보여 주고, 표 뒤의 문단은 각각 언제 적합한지 설명합니다.

작업에 사용자의 머신에만 있는 자원이 필요하다면 로컬에서 진행하십시오. 실제 로컬 데이터가 있는 데이터베이스, VPN으로 접속하는 서비스, GPU, 휴대폰 시뮬레이터, 책상 위의 하드웨어가 여기에 해당합니다. 각 변경 사항을 자신의 브라우저에서 몇 초 안에 확인하고 싶은 빠른 시각적 반복 작업이나, 조직이 클라우드 세션을 사용할 수 없게 하는 Zero Data Retention으로 운영되는 경우에도 로컬에서 진행하십시오.

두 방식의 중간에 위치한 기능이 두 가지 있습니다. 원격 제어(Remote control)는 세션을 사용자의 머신에 유지하면서 휴대폰이나 브라우저에서 세션을 조작할 수 있게 해 줍니다. Team 및 Enterprise 플랜에서 베타로 제공되는 자체 호스팅 환경은 조직의 자체 인프라에서 클라우드 세션을 실행하므로 사설 네트워크에 접근할 수 있습니다.

위 경우에 해당하지 않는다면 해당 작업은 클라우드에 적합한 후보입니다. 다음 섹션에서는 클라우드가 가장 큰 효과를 내는 워크플로를 다룹니다.

클라우드 세션에 적합한 7가지 워크플로

이 워크플로들은 표에서 본 차이점을 활용합니다. 작업마다 별도의 머신을 사용하고, 사용자가 자리를 비운 동안에도 세션이 계속 실행되며, 마지막에 검토할 브랜치가 남습니다.

1. 백로그 병렬 처리

서로 관련 없는 작은 수정 사항이 다섯 개 있다고 가정해 보겠습니다. 로컬에서는 하나씩 차례로 처리하거나, 워크트리 다섯 개를 만들어 각각의 포트와 설치 환경을 분리해서 관리해야 합니다. 클라우드에서는 세션 다섯 개를 시작하고 브랜치 다섯 개를 검토하면 됩니다.

CODEShell 
claude --cloud "Fix the flaky test in auth.spec.ts"
claude --cloud "Update the API documentation"
claude --cloud "Refactor the logger to use structured output"

claude --cloud는 현재 브랜치 기준으로 GitHub 리모트를 클론하므로, 먼저 로컬 커밋을 푸시하십시오. VM이 시작되는 동안 CLI는 설정 단계의 체크리스트를 실시간으로 표시하고, 사용자가 입력한 내용은 대기열에 추가합니다.

각 작업을 독립적으로 이해할 수 있는 티켓처럼 작성하여 무엇이 문제인지, 완료 상태가 어떤 모습인지, 어떻게 증명할지를 명시하십시오. 플래키 테스트(flaky test) 프롬프트에는 증명 방법이 지정되어 있었습니다. 테스트 스위트를 연속으로 30회 이상 실행하는 것이었습니다. 세션은 이를 40회 실행했습니다.

여러 작업이 하나의 큰 작업에 속할 때는 프로젝트(Pro와 Max 대상 공개 베타)가 코디네이터 대화를 실행하여 클라우드 세션을 대신 시작하고 추적합니다. 그런 다음 세션을 진행 중, 사용자 응답 대기 중, 검토 준비 완료의 상태별로 묶어서 보여줍니다.

2. 수정 사항의 증명 맡기기

플래키 테스트는 반복적인 증명이 필요한 작업의 가장 분명한 사례입니다. 테스트 스위트를 계속 반복해서 실행해야 하는데, 그 반복 작업이 작업 중인 머신을 붙잡고 있기를 바라지는 않을 것입니다. 클라우드에서 Claude는 캐시를 수정하고 명령 한 번으로 전체 테스트 스위트를 40회 실행했습니다.

VM에는 컴퓨팅 비용이 부과되지 않으며 CPU도 사용자의 것이 아니므로, 철저한 증명을 요청하셔도 좋습니다. 스위트를 200회 실행하거나, 50개 커밋에 걸쳐 리그레션을 이분 탐색(bisect)하거나, 느린 통합 테스트 계층을 실행하거나, 문서 세션이 했던 것처럼 앱을 띄운 뒤 curl로 호출해 볼 수 있습니다.

Claude의 각 턴은 여전히 사용자의 요금제 사용량에 포함되지만, 명령 하나 안에서 오래 실행되는 테스트는 비용이 거의 들지 않습니다. 포그라운드 명령은 기본적으로 2분 후(최대 10분) 타임아웃되며, 이후 백그라운드에서 최대 30분 더 계속 실행됩니다. 환경 변수에서 BASH_DEFAULT_TIMEOUT_MS와 BASH_MAX_TIMEOUT_MS로 기본값을 늘릴 수 있습니다.

3. 책상에서 계획하고, 클라우드에서 구현하고, 터미널에서 마무리하기

규모가 큰 변경은 의견을 주고받는 비용이 낮은 곳에서 먼저 접근 방식을 합의하십시오. 플랜 모드(plan mode)로 Claude를 시작하여 함께 계획을 세우고, 계획을 커밋한 뒤 푸시합니다.

CODEShell 
claude --permission-mode plan
# ...agree on the plan, save it to docs/migration-plan.md, commit and push...
claude --cloud "Execute the migration plan in docs/migration-plan.md"

클라우드 세션이 구현하는 동안 터미널은 다른 작업에 쓸 수 있습니다. 작업이 끝나면 세션을 내려받아 직접 마무리합니다.

CODEShell 
claude --teleport            # pick a cloud session
claude --teleport <session-id>

Teleport는 같은 저장소에 있는지 확인하고, 세션의 브랜치를 가져와 체크아웃하며, 대화 전체를 터미널로 불러옵니다. 작업 트리가 깨끗해야 하며(스태시를 제안합니다), 브랜치가 푸시되어 있어야 합니다. Claude Code 안에서는 /teleport(또는 /tp)로 같은 선택 화면을 열 수 있고, /tasks 다음에 t를 눌러도 됩니다. Desktop 앱은 반대 방향으로 동작하며, Open in 메뉴로 로컬 세션을 클라우드로 보냅니다.

4. 휴대폰으로 진행 상황 확인하기

Claude 앱의 Code 탭은 동일한 세션에 연결됩니다. 휴대폰에서 작업을 시작하고, 진행 상황을 따라가고, 방향을 조정하고, Claude가 던진 질문에 답하거나, Claude에게 풀 리퀘스트를 지켜보라고 지시할 수 있습니다.

휴대폰은 키보드 앞에 앉을 즈음이면 잊어버릴 만한 질문에 적합합니다. 저는 네 번째 세션에 휴대폰에서 입력할 법한 질문을 던졌습니다. tidepool은 조수를 어떻게 예측하며, 시간 구간의 경계에서는 어떤 문제가 생길 수 있는가 하는 질문이었습니다. Claude는 코드를 실행해 답을 검증했고 실제 버그를 찾아냈습니다. 루프가 첫 번째와 마지막 샘플을 검사하지 않기 때문에, 구간의 시작 지점에 정확히 위치한 만조를 API가 놓친다는 것이었습니다.

5. CI 실패와 리뷰 코멘트를 Claude에게 맡기기

저장소에 Claude GitHub App이 설치되어 있으면, 클라우드 세션이 풀 리퀘스트를 지켜보다가 그 PR에 일어나는 일에 대응할 수 있습니다. claude.ai/code의 세션에서 CI 바를 열고 Auto-fix를 켜십시오. 터미널에서 PR 브랜치에 대해 /autofix-pr을 실행하거나, 모바일 앱에 PR을 지켜보도록 요청하거나, 세션에 PR URL을 붙여 넣어도 됩니다.

Claude는 실패한 체크와 리뷰 코멘트에 대해 명확한 수정 사항을 푸시하고, 무엇을 바꿨는지 설명합니다. 모호하거나 아키텍처와 관련된 사안은 사용자에게 먼저 묻습니다. 리뷰 스레드의 답글은 사용자의 GitHub 사용자 이름으로 게시되며, Claude Code가 작성했다는 라벨이 붙습니다. Claude는 베이스 브랜치와의 머지 충돌에 대해서는 알림을 받지 않으므로, 리베이스가 필요하면 직접 요청하십시오. 또한 Claude의 코멘트가 Atlantis 같은 코멘트 기반 자동화를 트리거할 수도 있습니다.

6. 직접 시작하지 않고 작업 시작하기

루틴(routine)(리서치 프리뷰)은 프롬프트, 저장소, 커넥터, 환경처럼 하나의 작업을 수행하도록 설계된 여러 저장 리소스의 묶음입니다. 각 실행은 트리거가 시작하는 클라우드 세션입니다. 트리거는 스케줄(최소 간격은 1시간), 루틴 고유 엔드포인트에 대한 HTTP 호출, 또는 풀 리퀘스트 생성이나 릴리스 같은 GitHub 이벤트가 될 수 있습니다. 루틴은 claude.ai/code/routines, Desktop 앱, 또는 CLI의 /schedule로 만들 수 있습니다. 루틴은 승인 프롬프트 없이 실행되며, 기본적으로 claude/ 접두사가 붙은 브랜치로 푸시합니다.

여기에 도움이 되는 작은 도구가 두 가지 있습니다. 로그인되어 있는 어떤 머신에서든, CI 작업을 포함하여, 실행 중인 세션에 후속 작업을 대기열로 추가할 수 있습니다.

CODEShell 
claude -p "The integration tier is green now; rebase on main and push" --cloud <session-id>

미리 채워진 세션을 북마크해 둘 수도 있습니다. claude.ai/code?prompt=Triage+the+newest+issues&repositories=acme-labs/tidepool 같은 URL을 열면 프롬프트와 저장소가 이미 입력된 상태로 claude.ai/code가 열립니다.

7. 완전히 신뢰할 수 없는 코드 실행

기여자의 풀 리퀘스트, 새 의존성의 설치 스크립트, 5분 전에 클론한 저장소는 모두 읽어 보지 않은 코드를 실행할 수 있습니다. 노트북에서는 이런 코드가 SSH 키, 클라우드 CLI 세션, 브라우저 프로필과 같은 환경에서 실행됩니다. 클라우드 세션에서는 이 중 어느 것도 없는 일회용 VM에서, 세션 범위의 GitHub 자격 증명과 좁힐 수 있는 네트워크만으로 실행됩니다.

가장 엄격하게 실행하려면 환경의 네트워크 접근을 None으로 설정하고, 패키지 레지스트리, GitHub, 주요 클라우드 SDK 호스트를 허용하려면 Trusted를 유지하십시오. None이어도 Claude Code는 Anthropic API로 요청을 보내므로 그 경로로 데이터가 VM 밖으로 나갈 수 있고, 세션은 자신의 브랜치에 여전히 푸시할 수 있습니다. 모든 외부 트래픽은 호스트 이름을 기록하는 프록시를 거칩니다.

막힘 없이 GitHub 연결하기

첫 클라우드 세션이 잘못된다면 GitHub가 원인일 가능성이 가장 높습니다. 대부분의 문제는 클라우드 세션에 서로 다른 두 가지 GitHub 권한이 필요하다는 데서 비롯됩니다.

  • GitHub로 로그인하면 Claude가 사용자가 누구인지 알 수 있습니다.
  • 계정 또는 조직에 Claude GitHub App을 설치하면 Claude가 그곳의 어떤 비공개 저장소를 볼 수 있는지가 정해집니다.

공개 저장소는 첫 번째만으로 사용할 수 있습니다. 비공개 저장소는 해당 저장소를 소유한 계정 또는 조직에 두 번째 항목까지 필요합니다. GitHub를 연결했는데도 비공개 저장소가 보이지 않는다면, 대개 그 저장소를 소유한 계정 또는 조직에 App이 설치되어 있지 않은 경우입니다.

연결한 항목공개 저장소내 비공개 저장소조직의 비공개 저장소Auto-fix, GitHub 트리거, 프로젝트
GitHub 로그인만 한 경우예아니요아니요아니요
+ 개인 계정에 App 설치예예아니요내 저장소
+ 조직에 App 설치(소유자 승인)예내 계정에도 설치한 경우에만예조직 저장소
/web-setup (사용자의 gh 토큰)예예토큰이 접근할 수 있는 모든 저장소아니요, App 필요

경로 A: 브라우저에서 연결(권장)

claude.ai/connect-github에서 GitHub 계정을 연결한 다음, 저장소를 소유한 계정 또는 조직에 Claude GitHub App을 설치합니다. 조직의 경우 보통 소유자가 설치를 승인해야 합니다. 빠른 시작에서 각 단계를 차례로 안내합니다.

GitHub가 claude.ai/code로 돌려보내지 않는 경우, claude.ai/connect-github의 연결 페이지에서 일반적인 원인을 짧은 체크리스트로 확인할 수 있습니다. 그중 하나는 싱글 사인온(SSO) 단계로, 이 단계를 건너뛰면 조직의 저장소가 보이지 않습니다.

Auto-fix, GitHub로 트리거되는 루틴, 프로젝트도 App에 의존하므로 다른 방법으로 연결하더라도 App을 설치하십시오.

경로 B: /web-setup으로 터미널에서 연결

이미 gh CLI를 사용하고 있다면 Claude Code 안에서 /web-setup을 실행하여 gh 토큰을 Claude 계정으로 보냅니다. 그러면 App 설치 여부와 관계없이 세션이 해당 토큰으로 접근할 수 있는 모든 저장소에 접근할 수 있습니다. 자세한 절차는 터미널에서 연결하기를 참고하십시오. Team 및 Enterprise 플랜에서는 소유자가 먼저 Quick setup을 켜야 합니다.

경로 C: 일회성 작업이라면 GitHub 건너뛰기

GitHub 리모트가 없거나 App이 설치되지 않은 저장소에서 claude --cloud를 실행하면, Claude Code는 저장소를 클론하는 대신 저장소 번들을 업로드합니다. 세션은 사용자의 GitHub 연결에 해당 저장소에 대한 푸시 권한이 있는 경우에만 다시 푸시할 수 있습니다. 번들에 포함되는 항목과 제외되는 항목은 문서에 정리되어 있습니다.

Team 또는 Enterprise를 사용하는 경우

소유자는 다음과 같은 짧은 체크리스트를 따르면 됩니다. claude.ai/admin-settings/connectors에서 GitHub 커넥터를 켜고, Claude Code 관리자 설정에서 클라우드 세션을 허용하고, 조직의 저장소에 Claude GitHub App을 설치하거나 구성원의 요청을 승인하고, Quick setup을 켤지 결정합니다. IP 허용 목록(allowlist)을 사용하거나 GitHub Enterprise Server를 쓰는 조직은 추가 단계가 필요합니다. IP 허용 목록과 GitHub Enterprise Server 문서를 참고하십시오.

그래도 해결되지 않는 경우

증상원인해결 방법
선택 목록에 비공개 저장소가 나타나지 않습니다해당 저장소를 소유한 계정이나 조직에 앱이 설치되어 있지 않거나, 앱의 저장소 접근 범위에서 해당 저장소가 제외되어 있습니다해당 계정이나 조직에 앱을 설치하거나, GitHub 설정에서 앱의 Repository access에 해당 저장소를 추가합니다

그 밖의 문제는 문서의 문제 해결을 참고하십시오. GitHub를 연결한 뒤 저장소가 나타나지 않는 경우도 여기에 포함되어 있습니다. GitHub 연결을 완전히 해제하려면 claude.ai/customize/connectors를 사용합니다.

세션이 스스로 작업을 검증하는 데 필요한 것 제공

테스트를 실행할 수 있는 세션은 작업을 넘기기 전에 스스로 결과를 검증합니다. 그렇지 않으면 아무도 실행해 보지 않은 변경 사항을 검토해야 합니다. 이 가이드의 데모에서 얻은 가치 대부분은 Claude가 직접 실행한 것에서 나왔습니다. 테스트 스위트를 40번 실행하고, 서버를 띄워 curl로 호출하고, 구간 경계에서 조수 계산을 확인한 것이 그 예입니다. 10분 정도 환경을 설정하면 Claude가 이런 검증을 실행할 수 있게 됩니다.

  • Default 환경으로 시작합니다. Default 환경은 Trusted 네트워크 접근을 사용하며 변수와 설정 스크립트가 없습니다. 대부분의 JavaScript, Python, Go, Rust 저장소에는 이것으로 충분합니다.
  • 머신 설정에는 설정 스크립트를 사용합니다. 설정 스크립트는 Claude Code가 시작되기 전에 root 권한으로 실행되므로 apt install이 동작합니다. 스크립트는 반드시 종료 코드 0으로 끝나야 하며, 그렇지 않으면 세션이 시작되지 않습니다. 환경이 캐시되도록 약 5분 안에 끝나야 합니다. 이후 새 세션은 도구가 디스크에 설치된 스냅샷에서 시작됩니다. 캐시는 스크립트나 허용된 호스트를 변경할 때, 그리고 약 7일마다 다시 빌드됩니다.
  • 프로젝트 설정에는 SessionStart 훅(hook)을 사용합니다. npm install 같은 단계를 저장소의 .claude/settings.json에 있는 훅에 넣으면 로컬과 클라우드에서 동일하게 실행됩니다. 특정 단계를 클라우드에서만 실행해야 한다면 CLAUDE_CODE_REMOTE를 확인합니다. 저장소 훅은 단일 저장소 세션에서 로드됩니다.
  • 서비스는 세션마다 시작합니다. 캐시에는 파일이 저장됩니다. 실행 중이던 프로세스는 캐시에 남지 않습니다. Claude에게 service postgresql start를 실행하도록 요청하거나, SessionStart 훅에서 실행합니다.
  • 동작하는 범위에서 가장 좁은 네트워크 수준을 선택합니다. Trusted는 일반적인 레지스트리를 포함합니다. 비공개 레지스트리를 추가하려면 Custom을 사용하고, 작업에 공개 인터넷이 필요할 때만 Full을 사용합니다. 변경 사항은 약 1분 안에 실행 중인 세션에 반영됩니다.
  • 공유 변수에는 시크릿을 넣지 않습니다. 환경 변수는 해당 환경을 사용하는 모든 사람에게 보입니다. Pro와 Max에서는 환경의 API 자격 증명(API credentials)이 VM 외부에서, 지정한 호스트로 가는 요청에 키를 붙여 주므로 키가 변수에 남지 않습니다.
  • 명령어는 CLAUDE.md에 적어 둡니다. 개인 ~/.claude는 클라우드 VM에 전달되지 않습니다. Claude가 통합 테스트를 실행하는 방법을 알아야 한다면 저장소에 그 내용이 있어야 합니다.

효과를 보는 습관

  • 작업 하나에 세션 하나. 작고 분리된 세션은 검토하기 쉽고 버리는 비용도 적습니다.
  • 증거를 요청합니다. 작업이 끝났음을 증명하는 명령어를 지정하고, diff보다 먼저 Claude의 요약을 읽습니다.
  • claude --cloud 전에 푸시합니다. VM은 GitHub에서 클론하므로 푸시하지 않은 커밋은 VM에 전달되지 않습니다.
  • 긴 작업에서는 진행하면서 커밋합니다. 유휴 상태의 VM은 회수될 수 있습니다.
  • diff 보기에서 검토합니다. 인라인 코멘트는 다음 메시지에 묶여 전달되며, Create PR로 전체 PR, 초안(draft) PR, 또는 GitHub의 작성 페이지를 열 수 있습니다.
  • Claude가 작업하는 동안 방향을 조정합니다. Claude가 작업하는 중에 보낸 메시지는 대기열에 쌓이며, 대기 중인 메시지는 다시 회수할 수 있습니다.
  • 세션을 공유합니다. Team과 Enterprise에서는 세션의 공개 범위를 Team으로 설정하면 검토자가 변경이 어떻게 만들어졌는지 읽을 수 있습니다. 클라우드 세션의 커밋에는 대화 기록으로 연결되는 Claude-Session 트레일러가 포함됩니다.
  • 한도를 확인합니다. 병렬 세션은 요금제 한도를 병렬로 소모하므로, 세션 5개는 하나일 때보다 약 5배 빠르게 한도를 사용합니다. 루틴(Routines)에는 별도의 시간당 상한이 있으며, 프로젝트는 하루에 최대 200개의 새 스레드를 시작할 수 있습니다.

자주 묻는 질문

누가 클라우드 세션(cloud sessions)을 사용할 수 있나요? claude.ai 계정으로 로그인한 Pro, Max, Team 플랜 사용자와, 프리미엄 시트 또는 Chat + Claude Code 시트를 보유한 Enterprise 사용자가 사용할 수 있습니다. Console API 키나 서드파티 제공자로는 사용할 수 없습니다. 클라우드 세션 문서를 참고하십시오.

내 데이터는 어디로 가나요? Anthropic이 세션 트랜스크립트(transcript)를 저장하며, 보관 기간은 플랜과 모델 개선 설정에 따라 달라집니다. VM은 일정 시간 사용하지 않으면 회수되고, 세션을 삭제하면 해당 데이터도 함께 삭제됩니다. 데이터 사용과 보안을 참고하십시오.

Claude가 내 클라우드 세션 데이터로 학습하나요? 클라우드 세션도 Claude Code의 나머지 기능과 동일한 정책을 따릅니다. Team, Enterprise, API에서는 조직이 동의하지 않는 한 Anthropic이 사용자의 코드나 프롬프트로 모델을 학습하지 않습니다. Free, Pro, Max에서는 모델 개선 설정에 따라 달라집니다. 데이터 사용을 참고하십시오.

대규모 리포지토리도 처리할 수 있나요? VM의 사양은 약 4 vCPU, 16 GB RAM, 30 GB 디스크입니다. 무거운 설치 작업은 설정 스크립트(setup script)에 넣어 두십시오. 그러면 한 번만 실행되고 그 결과가 캐시된 스냅샷에 반영됩니다.

GitLab이나 Bitbucket은 어떤가요? claude --cloud는 모든 git 리포지토리에서 번들을 업로드할 수 있지만, 세션이 해당 호스트로 다시 푸시할 수는 없습니다. GitHub Enterprise Server는 Team과 Enterprise에서 지원됩니다. 플랫폼 제약 사항을 참고하십시오.

병렬 브랜치끼리 충돌하면 어떻게 되나요? 세션들은 서로의 존재를 알지 못합니다. 브랜치 하나를 먼저 머지한 다음, claude -p "rebase on main and fix any conflicts" --cloud <session-id>와 같이 다음 세션에 후속 요청을 보내십시오.

로컬 도구를 쓰지 못하게 되나요? 사용자 수준 설정은 클라우드로 옮겨지지 않으므로, 팀에 필요한 항목은 리포지토리로 옮겨야 합니다. 스킬과 명령어는 .claude/ 아래에 커밋하고, 프로젝트 범위의 MCP 서버는 .mcp.json에 추가하며, 테스트 명령어는 CLAUDE.md에 문서화하십시오. 클라우드 세션의 설정에서 각 세션이 읽어 들이는 항목을 확인할 수 있습니다.

5분 만에 시작

설정에는 약 5분이 걸립니다. 이후에는 작업을 맡기고 노트북을 닫은 뒤, 리뷰할 준비가 된 브랜치를 확인하러 돌아오면 됩니다.

  1. claude.ai/code를 열거나, Claude Code에서 claude.ai 계정으로 /login을 실행합니다.
  2. GitHub를 연결하고, 리포지토리가 있는 곳에 Claude GitHub App을 설치합니다.
  3. 리포지토리와 Default 환경을 선택합니다.
  4. 백로그에서 작업 하나를 골라, 완료 여부를 증명할 수 있는 명령어와 함께 Claude에게 맡깁니다.
  5. 탭을 닫습니다. 나중에 휴대폰으로 진행 상황을 확인한 다음, claude.ai/code에서 diff를 검토하고 풀 리퀘스트를 생성합니다.

You probably run Claude Code in a terminal on your own laptop. That session depends on the laptop in three ways:

  • It shares your working tree, so two sessions on one repository can edit the same files and fight over the same port.
  • It runs with your credentials.
  • It stops when your computer sleeps or the Wi-Fi drops.

A cloud session runs Claude Code on a machine of its own. Each task gets a fresh virtual machine with your repository cloned onto a new branch and your environment's setup already done.

You can start one from claude.ai/code, the Claude mobile app, the Desktop app, your terminal, and Slack. You can then follow it from the browser, the mobile app, and Desktop. When the work is done, it sits on a branch you can turn into a pull request.

Cloud sessions come with your Pro, Max, Team, or Enterprise plan at no additional cost: there's no separate charge for the cloud machine, and sessions draw on the same usage limits as the rest of Claude Code. Depending on your plan, an organization owner may need to turn on cloud sessions first.

For this guide I ran four real cloud sessions against a small sample repository. Their transcripts, diffs, and timings appear throughout. The repository and the user in the screenshots are made up. The work, the output, and the numbers come from those sessions.

One of the main advantages of cloud sessions is that you can run several tasks at once without them getting in each other's way. Here are three I started within 16 seconds of each other, each on its own machine. On my laptop, I'd have run these one after another, or spent my time keeping them out of each other's way.

THREE TASKS, ONE REPOSITORY, THREE MACHINES

The sample repository is tidepool, a small Node API that predicts tides for three fictional harbors. It had three ordinary problems: one test failed about one run in four, the API docs described parameters the code no longer read, and the logger built its lines by concatenating strings.

I started three cloud sessions within 16 seconds of each other, one per problem. I started them programmatically, and because tidepool isn't on GitHub, each session first recreated the repository from files in its prompt. With a real repository you'd skip that step, and from a terminal each session is one claude --cloud command. Shortened, the three prompts were:

CODEShell
claude --cloud "npm test fails maybe one run in four. Find the flaky test, fix the root cause in the code (not the test), and prove it by running the suite at least 30 times in a row."
claude --cloud "docs/API.md is out of date with src/server.js. Rewrite it so every endpoint, parameter, default and response shape matches the code. Start the server and run each curl example to check it."
claude --cloud "Make src/logger.js emit one JSON object per line, keep LOG_LEVEL, and log method, path, status and duration_ms as fields. Add a test for the logger."

The sessions ran for 61, 65 and 72 seconds, and all three were done 87 seconds after the first one started. Recreating the repository took roughly a third to just over half of each run. Here are the results.

  • The flaky test. Claude found a race in TtlCache.get. The cache stored a value only after the loader finished, so a second get for the same key during a load called the loader again. Claude changed the cache to store the in-flight promise, dropped the entry when a load fails, and ran npm test 40 times in a row with zero failures.
  • The docs. Claude started the server, ran a curl against every endpoint, and found five ways the old doc was wrong. It listed fields the API never returns, documented a days parameter the code ignores, gave heights in feet when they are metres, skipped the /next-high endpoint, and left out the error responses. It also found that a malformed from= value returns an empty list with a 200, and documented that as a caveat instead of changing server code it wasn't asked to touch.
  • The logger. Claude wrote the JSON logger, moved the request log to structured fields, and added five tests. Its commit went in with one failing test, so Claude reran the cache test eight times, saw it fail in five of them, and traced the failure to the same race the first session was fixing. It proposed the same fix, left the cache alone because that was outside its task, and said in its summary that the suite wasn't clean.

The logger result shows why cloud sessions suit parallel work. Each session had its own copy of the repository, its own processes and its own branch. The docs session and the logger session each started the API server to test against it, and neither affected the other. On a single laptop, two agents working in one checkout would edit the same files, and would collide on a port unless each picked its own.

Because of that isolation, the logger session had no access to the cache fix the first session was making. Split parallel tasks along file boundaries, merge the branches in a sensible order, and expect a session to report problems that another session is already fixing.

UNDER THE HOOD OF A CLAUDE CODE CLOUD SESSION

A cloud session is a Claude Code session running on Anthropic-managed infrastructure, or on your organization's own machines with a self-hosted environment. The figure shows the parts. The four takeaways after it are the ones that change how you work.

  • Every task gets its own machine. A fresh VM with your repository cloned onto a new branch, so sessions can't touch each other's files or ports. See what's installed.
  • Your GitHub token never enters the VM. A proxy holds it, and the session gets a short-lived credential that can push only to its own working branch. See the GitHub proxy.
  • The repository's Claude config comes along. Your personal one doesn't. CLAUDE.md, rules, skills, agents, and commands travel with the repo, and your ~/.claude stays on your laptop. See settings in cloud sessions.
  • Idle VMs get reclaimed. Reopen the session and you get a fresh VM with the conversation restored, so commit work you care about. See environment expiry.

For specs, permission modes, and network levels, see the cloud environments docs.

LOCAL OR CLOUD?

Cloud sessions don't replace local ones, and most people use both. The table shows where they differ, and the paragraphs after it say when each one fits.

Local sessionCloud session
Runs onYour machineA fresh VM for each task
Laptop asleep or offlineThe session stopsThe session keeps going
Several tasks on one repoSeparate worktrees, ports and careOne VM and one branch per task
What the agent can reachAnything your user account can, including SSH keys, cloud CLIs and ~/.claudeThe repository, the network level you set, the connectors you enable, and a session-scoped GitHub credential
Start or follow fromThat machine, or your phone through remote controlBrowser, phone, Desktop, terminal, Slack, an API call or a schedule

Ends withChanges in your working treeA branch, and a pull request when you want one
ComputeYour machineNo separate compute charge; uses your plan's limits

Stay local when the task needs something only your machine has. That covers a database with real local data, a service you reach over VPN, a GPU, a phone simulator, or hardware on your desk. Stay local too for tight visual loops where you want to see each change in your own browser within seconds, and when your organization runs with Zero Data Retention, which turns cloud sessions off.

Two features sit between the options. Remote control keeps the session on your machine and lets you steer it from your phone or browser. Self-hosted environments, in beta for Team and Enterprise, run cloud sessions on your organization's own infrastructure, so they can reach private networks.

If none of that applies, the task is a good candidate for the cloud. The next section covers the workflows where that pays off most.

SEVEN WORKFLOWS THAT SUIT CLOUD SESSIONS

These workflows put the differences in the table to work: a separate machine for each task, sessions that keep running while you're away, and a branch at the end for you to review.

1. Clear a backlog in parallel

Let's say you have five small, unrelated fixes. Locally, you'd do them one after another, or set up five worktrees and keep their ports and installs apart. In the cloud, you'd start five sessions and review five branches.

CODEShell
claude --cloud "Fix the flaky test in auth.spec.ts"
claude --cloud "Update the API documentation"
claude --cloud "Refactor the logger to use structured output"

claude --cloud clones your GitHub remote at your current branch, so push your local commits first. While the VM starts, the CLI shows a live checklist of setup steps and queues anything you type.

Write each task as a self-contained ticket that states what's wrong, what done looks like, and how to prove it. The flaky-test prompt named its proof: running the suite at least 30 times in a row. The session ran it 40 times.

When the tasks belong to one larger effort, a project (public beta for Pro and Max) runs a coordinator conversation that starts and tracks the cloud sessions for you. It then groups them by state: working, waiting on you, and ready for review.

2. Let it prove the fix

A flaky test is the clearest case of work that needs repeated proof: you have to run the suite again and again, and you don't want that loop tying up the machine you're working on. In the cloud, Claude patched the cache and ran the whole suite 40 times in one command.

The VM has no compute charge and its CPU isn't yours, so ask for thorough proof. Run the suite 200 times, bisect a regression across 50 commits, run the slow integration tier, or start the app and hit it with curl the way the docs session did.

Each of Claude's turns still counts toward your plan, but a long test run inside one command costs little. Foreground commands time out after 2 minutes by default (10 at most) and then keep running in the background for up to 30 more. You can raise the defaults with BASH_DEFAULT_TIMEOUT_MS and BASH_MAX_TIMEOUT_MS in the environment's variables.

3. Plan at your desk, build in the cloud, finish in your terminal

For a larger change, agree on the approach first where back-and-forth is cheap. Start Claude in plan mode, work out the plan together, commit the plan, and push it.

CODEShell
claude --permission-mode plan
# ...agree on the plan, save it to docs/migration-plan.md, commit and push...
claude --cloud "Execute the migration plan in docs/migration-plan.md"

While the cloud session builds, your terminal is free for other work. When it's done, pull the session down to finish it by hand.

CODEShell
claude --teleport            # pick a cloud session
claude --teleport <session-id>

Teleport checks that you're in the same repository, fetches the session's branch, checks it out, and loads the whole conversation into your terminal. You need a clean working tree (it offers to stash), and the branch has to be pushed. From inside Claude Code, /teleport (or /tp) opens the same picker, and /tasks then t works too. The Desktop app goes the other way, and its Open in menu sends a local session to the cloud.

4. Check in from your phone

The Code tab in the Claude app connects to the same sessions. From your phone you can start a task, follow it, steer it, answer a question Claude asked, or tell Claude to watch a pull request.

A phone suits questions you'd otherwise forget by the time you reach a keyboard. I gave a fourth session the kind of question you'd type on one: how does tidepool predict tides, and how could it go wrong at the edges of a time window? It ran code to check its answer and found a real bug. The loop never examines the first or last sample, so the API misses a high tide that falls exactly at the start of the window.

5. Hand CI failures and review comments to Claude

With the Claude GitHub App installed on a repository, a cloud session can watch a pull request and act on what happens to it. From the CI bar in a session at claude.ai/code, turn on Auto-fix. You can also run /autofix-pr on the PR branch in your terminal, ask the mobile app to watch the PR, or paste the PR URL into a session.

Claude pushes clear fixes for failing checks and review comments, and explains what it changed. It asks you about anything ambiguous or architectural. Replies on review threads post under your GitHub username, labeled as Claude Code. Claude doesn't get notified about merge conflicts with the base branch, so ask it to rebase. Its comments can also trigger comment-driven automation such as Atlantis.

6. Start work without starting it yourself

A routine (research preview) is several saved resources designed to accomplish a task, such as a prompt, repositories, connectors, and an environment. Each run is a cloud session, started by a trigger. Triggers can be a schedule (hourly at most often), an HTTP call to the routine's own endpoint, or a GitHub event such as a pull request opening or a release. Create one at claude.ai/code/routines, in the Desktop app, or with /schedule in the CLI. Routines run without approval prompts, and by default they push to claude/-prefixed branches.

Two smaller tools help here. You can queue a follow-up into a running session from any machine where you're logged in, including a CI job.

CODEShell
claude -p "The integration tier is green now; rebase on main and push" --cloud <session-id>

You can also bookmark a prefilled session. A URL such as claude.ai/code?prompt=Triage+the+newest+issues&repositories=acme-labs/tidepool opens claude.ai/code with the prompt and repository already filled in.

7. Run code you don't fully trust

A contributor's pull request, a new dependency's install script, or a repository you cloned five minutes ago can all run code you haven't read. On your laptop, that code runs next to your SSH keys, your cloud CLI sessions and your browser profile. In a cloud session it runs in a disposable VM with none of those, a session-scoped GitHub credential, and a network you can narrow.

Set the environment's network access to None for the strictest run, or keep Trusted, which allows package registries, GitHub and the major cloud SDK hosts. Even at None, Claude Code still sends requests to the Anthropic API, so data can leave the VM that way, and the session can still push to its own branch. All outbound traffic passes through a proxy that logs hostnames.

CONNECTING GITHUB WITHOUT GETTING STUCK

If your first cloud session goes wrong, GitHub is the most likely reason. Most problems come from cloud sessions needing two separate GitHub permissions.

  • Signing in with GitHub tells Claude who you are.
  • Installing the Claude GitHub App on an account or organization sets which private repositories Claude can see there.

Public repositories work with the first alone. Private repositories need the second, on whichever account or organization owns them. If you connected GitHub and a private repository is missing, the App usually isn't installed on the account or organization that owns it.

What you've connectedPublic reposYour private reposAn org's private reposAuto-fix, GitHub triggers, projects
Signed in with GitHub onlyYesNoNoNo
+ App on your personal accountYesYesNoYour repos
+ App on the organization (owner approves)YesOnly if also on your accountYesOrg repos
/web-setup (your gh token)YesYesWhatever your token can reachNo, needs the App

Path A: connect in the browser (recommended)

Connect your GitHub account at claude.ai/connect-github, then install the Claude GitHub App on the account or organization that owns your repository. For an organization, an owner usually has to approve the install. The quickstart walks through each step.

If GitHub doesn't send you back to claude.ai/code, the connect page at claude.ai/connect-github can show a short checklist for the usual causes. One of them is the single sign-on step, which hides an organization's repositories if you skip it.

Auto-fix, GitHub-triggered routines and projects also depend on the App, so install it even if you connect another way.

Path B: connect from your terminal with /web-setup

If you already use the gh CLI, run /web-setup inside Claude Code to send your gh token to your Claude account. Sessions can then reach any repository that token can, with or without the App. See Connect from your terminal for the walkthrough. On Team and Enterprise plans, an owner has to turn on Quick setup first.

Path C: skip GitHub for a one-off

Run claude --cloud in a repository that has no GitHub remote, or one where the App isn't installed, and Claude Code uploads a bundle of your repository instead of cloning it. The session can push back only if your GitHub connection has push access to that repository. The docs list what the bundle includes and leaves out.

If you run Team or Enterprise

An owner has a short checklist: turn on the GitHub connector at claude.ai/admin-settings/connectors, allow cloud sessions in the Claude Code admin settings, install the Claude GitHub App on the organization's repositories (or approve members' requests), and decide whether to turn on Quick setup. Organizations with IP allowlists or GitHub Enterprise Server have an extra step. See the docs on IP allowlists and GitHub Enterprise Server.

GIVE SESSIONS WHAT THEY NEED TO CHECK THEIR OWN WORK

A session that can run your tests checks its own work before it hands the work back. Without that, you review changes nobody has run. Most of the value in this guide's demos came from Claude running things: the suite 40 times, the server and its curls, the tide calculation at the window's edge. Ten minutes of environment setup gives Claude a way to run those checks.

  • Start with the Default environment. It uses Trusted network access, no variables and no setup script, which is enough for most JavaScript, Python, Go and Rust repositories.
  • Use a setup script for the machine. It runs as root before Claude Code starts, so apt install works. It must exit 0 or the session won't start, and it should finish within about five minutes so the environment gets cached. After that, new sessions start from a snapshot with your tools on disk. The cache rebuilds when you change the script or the allowed hosts, and about every seven days.
  • Use a SessionStart hook for the project. Put npm install and similar steps in a hook in the repository's .claude/settings.json, so they run the same way locally and in the cloud. Check CLAUDE_CODE_REMOTE if a step should run only in the cloud. Repository hooks load in single-repository sessions.
  • Start services per session. The cache stores files. Processes that were running don't survive it. Ask Claude to run service postgresql start, or do it in a SessionStart hook.
  • Pick the narrowest network level that works. Trusted covers the common registries. Use Custom to add a private registry, and Full only when the task needs the open internet. Changes reach running sessions within about a minute.
  • Keep secrets out of shared variables. Environment variables are visible to anyone who uses the environment. On Pro and Max, an environment's API credentials attach a key to requests for the hosts you name, outside the VM, so the key never sits in a variable.
  • Put the commands in CLAUDE.md. Your personal ~/.claude doesn't reach the cloud VM. If Claude needs to know how to run the integration tests, the repository has to say so.

HABITS THAT PAY OFF

  • One task, one session. Small, separate sessions are easier to review and cheaper to throw away.
  • Ask for evidence. Name the command that proves the task is done, and read Claude's summary before the diff.
  • Push before claude --cloud. The VM clones from GitHub, so unpushed commits don't reach it.
  • Commit as you go on long tasks. Idle VMs can be reclaimed.
  • Review in the diff view. Inline comments are batched into your next message, and Create PR can open a full PR, a draft, or GitHub's compose page.
  • Steer while Claude works. Messages you send while Claude works queue up, and you can take a queued one back.
  • Share the session. On Team and Enterprise, set a session's visibility to Team so a reviewer can read how the change was made. Commits from cloud sessions carry a Claude-Session trailer that links back to the transcript.
  • Watch your limits. Parallel sessions draw on your plan limits in parallel, so five sessions use them about five times as fast as one. Routines have their own hourly caps, and projects can start up to 200 new threads a day.

COMMON QUESTIONS

Who can use cloud sessions? Pro, Max, and Team plans, and Enterprise users with a premium seat or a Chat + Claude Code seat, signed in with a claude.ai account. They aren't available with a Console API key or a third-party provider. See the cloud sessions docs.

Where does my data go? Anthropic stores the session transcript, and how long it's kept depends on your plan and model-improvement setting. VMs are reclaimed after inactivity, and deleting a session removes its data. See data usage and security.

Will Claude train on my cloud sessions data? Cloud sessions follow the same policy as the rest of Claude Code. On Team, Enterprise, and the API, Anthropic doesn't train models on your code or prompts unless your organization opts in. On Free, Pro, and Max, it depends on your model-improvement setting. See data usage.

Will it handle my large repository? The VM has about 4 vCPUs, 16 GB of RAM, and 30 GB of disk. Put heavy installs in a setup script so they run once and land in the cached snapshot.

What about GitLab or Bitbucket? claude --cloud can upload a bundle from any git repository, but the session can't push back to those hosts. GitHub Enterprise Server is supported on Team and Enterprise. See the platform restrictions.

What happens when parallel branches conflict? The sessions don't know about each other. Merge one branch, then send the next session a follow-up such as claude -p "rebase on main and fix any conflicts" --cloud <session-id>.

Will I lose my local tools? User-level config doesn't travel, so move what the team needs into the repository: commit skills and commands under .claude/, add project-scoped MCP servers to .mcp.json, and document test commands in CLAUDE.md. Settings in cloud sessions lists what each session reads.

START IN FIVE MINUTES

Setup takes about five minutes. After that, you can hand off a task, close your laptop, and come back to a branch that's ready for review.

  1. Open claude.ai/code, or run /login in Claude Code with your claude.ai account.
  2. Connect GitHub and install the Claude GitHub App where your repository lives.
  3. Pick the repository and the Default environment.
  4. Give Claude one task from your backlog, with a command that proves it's done.
  5. Close the tab. Check in from your phone later, then review the diff and create the pull request at claude.ai/code.
