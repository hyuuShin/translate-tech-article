OpenAI의 OpenClaw 같은 지속형 에이전트 보안 강화

Securing persistent agents like OpenClaw at OpenAI

OpenAI가 신뢰할 수 있는 컨트롤 플레인(control-plane) 서비스, Codex 샌드박싱(sandboxing), 자동 검토(auto-review), 에이전트 아이덴티티(agent identity), 관측 가능성(observability)을 결합하여 지속형 에이전트를 운영하는 방법입니다.

How OpenAI combines trusted control-plane services, Codex sandboxing, auto-review, agent identity, and observability to run persistent agents.

OpenClaw가 약 1년 전 출시되었을 때, 지속형 에이전트(persistent agent)의 역량을 세상에 보여 주었습니다. 목표가 고정되어 있고 사람이 방향을 조정하는 일반적인 codex 세션과 달리, 지속형 에이전트는 넓은 범위를 대상으로 24시간 내내 실행되며 사용자의 입력이 없어도 선제적으로 작업을 수행할 수 있습니다.

지속형 에이전트는 매우 강력하지만, 실제 환경에 배포된 사례는 지금까지 제한적이었습니다. 이러한 배포는 기존 소프트웨어와 비교해 새로운 과제를 많이 안겨 줍니다. 기존 소프트웨어에서는 설정과 코드가 결정적(deterministic)이라고 가정했고, 위협도 (대부분) 외부 공격자에게서 온다고 보았습니다. 반면 지속형 에이전트는 목표를 달성하기 위해 자신의 설정을 변경하고 임의의 코드를 작성할 수 있습니다. 에이전트가 의도에서 벗어난(misaligned) 행동을 하면 공격은 내부에서 발생합니다.

OpenAI는 현재 수백 개의 OpenClaw 에이전트를 포함해 회사 전반에 지속형 에이전트를 배포해 운영하고 있습니다. 이 글에서는 OpenAI에서 OpenClaw 배포를 가능하게 하기 위해 도입한 통제 방안 중 일부를 소개합니다.

신뢰 영역과 비신뢰 영역의 실행 분리

지속형 에이전트를 안전하게 운영하려면 신뢰할 수 있는 결정적 로직을 신뢰할 수 없는 LLM 실행과 분리해야 했습니다. 신뢰할 수 있는 로직에는 네트워킹, 아이덴티티, 샌드박싱 같은 핵심 구성 요소가 포함됩니다. 이는 소프트웨어 버그를 제외하면 설정된 대로 동작해야 하는 전통적인 정적 코드입니다. 반면 에이전트, 에이전트가 실행되는 환경, 에이전트가 작성하는 코드는 신뢰할 수 없는 대상으로 간주합니다. 이 환경에서는 에이전트가 목표를 달성하기 위해 코드를 동적으로 생성할 수 있으며, 그 동작에 대해서는 어떠한 강력한 보장도 없습니다.

OpenClaw에서 이를 지원하기 위해 오픈 소스 프로젝트에 원격 하네스 실행(remote harness execution) 기능을 구현했습니다. 이를 통해 OpenClaw Gateway를 에이전트 하네스와 별도의 컨테이너(저희의 경우에는 별도의 클러스터)에서 실행할 수 있게 되었습니다.

이렇게 분리한 덕분에 에이전트를 설정하는 구성 요소인 게이트웨이는 신뢰할 수 있는 결정적 코드로 취급하고, 에이전트 워크로드는 신뢰할 수 없는 코드로 보고 샌드박싱에 집중할 수 있었습니다.

강력한 보안 경계 적용

에이전트 워크로드의 보안 경계는 에이전트가 수행할 수 있는 행동을 제한하는 샌드박싱을 통해 강제합니다.

OpenClaw 배포에는 다음과 같은 샌드박스 통제를 사용했습니다.

  • 네트워크: 에이전트가 접근할 수 있는 엔드포인트를 통제합니다. 조직에서 관리하는 허용 목록(allowlist)을 사용하고, 제한 대상 엔드포인트는 명시적으로 차단했습니다.
  • 워크스페이스: 에이전트가 접근할 수 있는 파일을 통제합니다. 에이전트 작업 디렉터리에만 쓰기를 허용했습니다.
  • 프로세스: 에이전트가 접근할 수 있는 프로세스를 통제합니다. codex linux sandbox를 통한 프로세스 격리를 활용했습니다.
  • 시크릿: 에이전트가 접근할 수 있는 시크릿을 통제합니다. 시크릿은 자격 증명 브로커(credential broker)를 통해 관리하므로 에이전트에게 노출되지 않습니다.

OpenClaw 배포에는 codex 하네스에 내장된 샌드박스를 사용했습니다. 아래는 적용한 설정의 일부이며, requirements.toml(codex 설정에서 사용할 수 있는 옵션을 제한)과 config.toml(실제 codex 설정)로 나누어 정리했습니다. 이와 함께 몇 가지 추가 보안 통제도 활성화했습니다. danger-full-access 모드를 사용할 수 없도록 했고, 웹 검색 쿼리를 OpenAI 자체 인덱스로 라우팅하는 캐시된 웹 검색(cached web search)을 사용했습니다.

requirements.toml

# Exclude unrestricted "danger-full-access" sandbox mode.
allowed_sandbox_modes = ["read-only", "workspace-write"]

# Permit cached hosted search, but not live hosted search.
allowed_web_search_modes = ["cached"]

# Require the managed network proxy.
experimental_network.enabled = true

# Prevent user-level configuration from expanding the domain allowlist.
experimental_network.managed_allowed_domains_only = true

# Allow only these destinations; replace with the workload's required hosts.
experimental_network.allowed_domains = [
  "github.com",
  "api.github.com",
  "codeload.github.com",
]

# Explicitly block these destinations, including cloud metadata endpoints.
experimental_network.denied_domains = [
  "pastebin.com",
  "*.pastebin.com",
  "webhook.site",
  "metadata.google.internal",
  "169.254.169.254",
]

config.toml

# Select the permission profile defined below.
default_permissions = "openclaw"

# Use cached hosted search.
web_search = "cached"

[permissions.openclaw.filesystem]
# Allow reads needed by the minimal runtime environment.
":minimal" = "read"

# Allow reading and modifying the agent's workspace.
"/home/dev-user/openclaw-workspaces" = "write"

# Allow reading managed assets without modifying them.
"/home/dev-user/read-only" = "read"

# Prevent access to SSH credentials.
"/home/dev-user/.ssh" = "deny"

[permissions.openclaw.network]
# Permit network access through the administrator-required proxy.
enabled = true

# Do not inherit an upstream proxy.
allow_upstream_proxy = false

# Keep the proxy's local/private-address guard enabled.
allow_local_binding = false

# Disable the SOCKS5 listener.
enable_socks5 = false

# Disable SOCKS5 UDP support.
enable_socks5_udp = false

# Do not permit proxy listeners on non-loopback addresses.
dangerously_allow_non_loopback_proxy = false

# Do not permit unrestricted Unix-socket access.
dangerously_allow_all_unix_sockets = false

[shell_environment_policy]
# Preserve default filtering of sensitive environment variables.
ignore_default_excludes = false

# Remove GitHub credentials from agent command environments.
# This does not hide credentials stored in accessible files.
exclude = [
  "GH_TOKEN",
  "GITHUB_TOKEN",
  "OPENCLAW_GITHUB_BASIC_AUTH",
  "OPENCLAW_GITHUB_READONLY_BASIC_AUTH",
]

[apps._default]
# Disable apps unless individually enabled.
enabled = false

# Disable destructive app operations by default.
destructive_enabled = false

# Disable open-world app operations by default.
open_world_enabled = false

모델 기반 보호 장치 추가

지금까지 설명한 통제는 모두 기존의 결정적 코드에 의존해 에이전트가 의도에서 벗어난 행동을 하지 못하도록 막는다는 점에서 정적입니다. 모델이 더 똑똑해질수록 컴퓨팅 규모에 맞춰 확장되는 방어 수단, 즉 다른 모델도 함께 갖추는 것이 중요합니다.

Auto-review를 사용하면 두 번째 에이전트가 주 에이전트의 행동을 모니터링하고 승인할 수 있습니다. 사람의 검토를 계속 요구하면 검토 피로가 생겨, 사람이 모든 권한 요청을 무심코 수락하도록 길들여집니다. LLM 기반 리뷰어를 필터로 사용하면 사람의 주의를 가치가 높은 승인 건에 집중시킬 수 있습니다. 이 기능은 OpenClaw와 Codex 모두에서 기본적으로 지원됩니다.

OpenClaw 배포에서는 모든 에이전트 행동에 auto review를 적용하고 있습니다.

에이전트 아이덴티티와 사용자 아이덴티티 분리

에이전트가 행동을 수행할 때는 해당 행동을 감사하고, 에이전트에게 리소스 접근 권한을 부여하며, 그 행동이 에이전트가 시작한 것인지 사용자가 시작한 것인지 구분할 수 있어야 합니다. 에이전트 아이덴티티는 이를 가능하게 하는 수단입니다. 에이전트에게 리소스에 대한 고유한 접근 권한을 부여하는 WAG 같은 사양과, OAuth 위임을 통해 에이전트가 사용자를 대신해 행동할 수 있게 하는 XAA 같은 사양이 새롭게 등장하고 있습니다. 에이전트 아이덴티티는 봇에 별도의 API 접근을 제공하는 서비스 계정과는 다르다는 점에 유의해야 합니다. 두 가지는 함께 사용해야 합니다. 예를 들어 에이전트는 자신의 에이전트 아이덴티티로 행동하고, 해당 아이덴티티에 연결된 서비스 계정을 통해 서드파티 서비스에 접근해야 합니다.

OpenClaw 배포에서는 각 에이전트가 ChatGPT Service Account와 연결된 고유한 아이덴티티를 가집니다. 이를 통해 각 에이전트는 사용자와 분리된 자체 추론(inference) 자격 증명을 갖게 되고, 팀은 에이전트에 맞춤형 플러그인을 연결할 수 있습니다. 또한 에이전트의 행동을 감사할 수 있고, 필요한 경우 추론을 중단시킬 수도 있습니다.

모든 활동의 관측

포괄적인 관측 가능성(observability)이 있으면 운영자는 에이전트가 어떻게 설정되었는지부터 어떤 행동을 했는지까지 에이전트의 전체 수명 주기를 파악할 수 있습니다. 지속형 에이전트에서는 의도에서 벗어난 행동을 추적하고 탐지하기 위해 이러한 범위의 관측을 갖추는 것이 매우 중요합니다.

OpenClaw 배포 환경에서는 컨트롤 플레인(control plane)의 모든 구성 변경과 에이전트의 모든 턴(turn)을 로그로 기록합니다. 에이전트의 턴에는 민감한 정보가 포함될 수 있으므로, 이 로그는 접근이 엄격히 제한되어 있으며 보안팀의 소수 인원만 열람할 수 있습니다.

맺음말

지속형 에이전트(persistent agent)를 배포하는 일은 아직 도입 곡선의 초기 단계에 있습니다. 확립된 모범 사례가 부족하기 때문에, 오늘날 많은 기업에서 에이전트를 도입하기가 어렵습니다.

OpenAI에서 OpenClaw 내부 파일럿을 도입했을 때, 회사 전반의 기술 팀과 비기술 팀 모두에서 생산성과 도입률이 크게 향상되는 것을 확인했습니다. 현재는 백그라운드에서 능동적으로 실행되며 의미 있는 작업을 수행하는 에이전트가 500개 이상 있습니다. 제품 피드백에 따라 PR을 자동으로 여는 작업부터 새로운 기능에 대한 데이터 실험을 지속적으로 실행하는 작업까지 다양합니다.

OpenAI dev day에서 벤더 중립적인 오픈 소스 에이전트 컨트롤 플레인인 OpenClaw Enterprise(OCE)를 발표했습니다. OCE를 사용하면 표준 codex 프리셋을 사용할 때 앞서 설명한 여러 안전장치가 내장된 상태로 에이전트를 실행할 수 있습니다. 이 프로젝트는 현재 파일럿 단계이며, 올해 말까지 1.0 버전을 출시할 계획입니다.

산업 전반에서 AI가 가져올 가장 큰 성과 중 상당수는 지속형 에이전트에서 나올 것이라고 생각합니다. 저희가 배운 내용을 공유하고 OCE를 공개적으로 개발함으로써, 누구나 더 안전하게 에이전트를 배포할 수 있기를 바랍니다.

When OpenClaw launched almost a year ago, it showed the world the capabilities of a persistent agent. Unlike regular codex sessions which involve a fixed goal and human steering, persistent agents run 24/7 with a broad scope and the ability to proactively take actions without user input.

While persistent agents are extremely capable, their real world deployment has been limited to date. These deployments present many novel challenges compared to traditional software. With traditional software, we have relied on configuration and code to be deterministic and for threats to come (mostly) from external attackers. Persistent agents can change their configuration and write arbitrary code to accomplish a goal. Attacks come from the inside when agents take misaligned actions.

At OpenAI, we currently have persistent agents deployed across the entire company, including hundreds of OpenClaw agents. This post covers some of the controls we’ve adopted to enable OpenClaw deployments at OpenAI.

Separate trusted and untrusted execution

In order to secure persistent agents, we needed to isolate trusted deterministic logic from un-trusted LLM execution. Trusted logic includes critical components like networking, identity, and sandboxing. This is traditional static code that, outside of software bugs, should behave as configured. Agents, the environment they execute in, and the code they write are considered untrusted. This is an environment where agents can dynamically generate code to accomplish a goal with no hard guarantees on behavior.

To support this in OpenClaw, we ended up implementing remote harness execution in the open source project. This enabled the OpenClaw Gateway to run in a separate container (and in our case, a separate cluster), from the agent harness.

By implementing the split, we could treat the gateway, the component that configured the agent, as trusted deterministic code and focus on sandboxing the agent workload as untrusted code.

Enforce hard security boundaries

Security boundaries for agent workloads are enforced through sandboxing, which limits the actions agents can take.

For our OpenClaw deployment, we used the following sandbox controls:

  • network: control what endpoints an agent can access - we used an organization-managed allowlist with explicit denials for restricted endpoints
  • workspace: control what files an agent can access - we only allowed writes to agent working directories
  • process: control what processes an agent can access - we relied on process isolation via codex linux sandbox
  • secrets: control what secrets an agent can access - we manage secrets through a credential broker so secrets are not visible to the agent

For our OpenClaw deployment, we used the built-in sandbox from the codex harness. The following are some of the settings we employed, divided between requirements.toml (restrict what options are available in codex configuration) and config.toml (actual codex configuration). Note that we also enabled some additional security controls - removing the ability to use danger-full-access mode and relying on cached web search which routes web searches through OpenAI’s own index for search queries.

Add model-based safeguards

All the controls we talked about so far are static in the sense that they rely on traditional deterministic code to prevent an agent from taking misaligned actions. As models get smarter, it’s critical that we also have defenses that scale with compute - aka other models.

With Auto-review, a second agent can monitor and approve the actions of a primary agent. Constantly requiring human review creates review fatigue where humans are trained to blindly accept all permission prompts. By using an LLM based reviewer as a filter, we reserve human attention for high value approvals. This is a feature that is natively supported in both OpenClaw and Codex.

For our OpenClaw deployment, we enforce auto review on all agent actions.

Split agent identity from user identity

When an agent takes an action, we need to be able to audit said action, give the agent access to resources, and distinguish whether that action was initiated by the agent or by the user. Agent identity gives us the means to do so. There are emerging specifications like WAG that give agents their own access to resources, and others like XAA that let agents act on behalf of the user through OAuth delegation. Note that agent identity is different from service accounts which provide separate API access for bots. The two should be used together - for example, your agent should act with its own agent identity and access third party services through service accounts which are linked to said identity.

For our OpenClaw deployment, each agent has a unique identity that is associated with a ChatGPT Service Account. This gives each agent its own inference credential separate from the user’s and allows teams to connect custom plugins to the agent. This also lets us audit agent actions and if needed, turn off inference.

Observe everything

Comprehensive observability lets operators understand the full lifecycle of agents - from how they were configured to what actions they took. With persistent agents, it’s critical that we have this coverage in order to trace and detect misaligned actions.

For our OpenClaw deployment, we log everything - every configuration change on the control plane and all turns from the agent. Because agent turns can contain sensitive information, these logs are locked down and only available to a select few individuals in the security team.

Closing thoughts

We are still at the beginning of the adoption curve when it comes to deploying persistent agents. The lack of established best practices makes it difficult to adopt agents in many enterprises today.

When we rolled out our internal pilot of OpenClaw at OpenAI, we witnessed a huge jump in both productivity and adoption, from both technical and non-technical teams across the company. We now have over 500 agents that run proactively in the background doing meaningful work - everything from automatically opening PRs in response to product feedback to continuously running data experiments on new features.

During OpenAI dev day, we announced OpenClaw Enterprise (OCE), an open source vendor neutral agent control plane. If you use OCE, you can launch an agent with many of the safeguards we talked about built-in when using the standard codex preset. Note the project is currently still in the pilot phase and that we plan to get to a 1.0 release by the end of the year.

We believe many of AI’s biggest gains in industry will come from persistent agents. By sharing what we’ve learned and building OCE in the open, we hope to make them safer for everyone to deploy.
